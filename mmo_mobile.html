BRIEFING

LE CONCEPT

Les jeux de stratégie mobiles comme Rise of Kingdoms font cohabiter des milliers de joueurs sur une même carte. Ce projet en construit la fondation : un serveur autoritaire écrit de zéro en C++20, sans moteur, qui gère plusieurs royaumes dans un seul processus, et un client mobile Unity qui partage avec lui un protocole binaire généré. Le client ne décide de rien : toute la logique de jeu vit côté serveur.

EnTT (ECS) ENet FlatBuffers SQLiteCpp libsodium nlohmann/json spdlog Unity
ARCHITECTURE

UN PROCESSUS, PLUSIEURS ROYAUMES

  • > Partitions logiques Chaque royaume (déclaré dans kingdoms.json) possède sa propre registry ECS, sa grille spatiale et ses systèmes de gameplay. Ajouter une mécanique = implémenter IGameSystem.
  • > Zéro reconnexion Le joueur garde une connexion unique du login au gameplay, même en changeant de royaume. Ses ressources sont stockées par clé composite (account_id, kingdom_id).
  • > Boucle à tick fixe GameLoop enchaîne réception réseau → logique → envoi, à 20 Hz par défaut (paramétrable). Les callbacks des autres threads sont remis au thread principal par une file thread-safe.

NETWORK PROTOCOL

PROTOCOLE BINAIRE PARTAGÉ C++ / C#

Les messages sont décrits en FlatBuffers (un fichier .fbs par domaine : Auth, Kingdom, Resources, Movement) et encapsulés dans une enveloppe universelle Opcode + payload. Un script compile les schémas, génère les headers C++ du serveur et copie les classes C# directement dans le projet Unity : les deux côtés ne peuvent pas diverger.

01 — CONNECTC2S_Login → S2C_LoginResult + jeton de session
▶
02 — ROYAUMESC2S_RequestKingdoms → S2C_KingdomList
▶
03 — SÉLECTIONprofil chargé en base, entité ECS créée → S2C_PlayerData
▶
04 — GAMEPLAYC2S_ModifyResources → S2C_ResourceUpdate

Les opcodes sont groupés par plages (1-999 général, 1000-1999 mouvement, 2000-2999 combat…) et routés vers des handlers dédiés via un PacketDispatcher.

SYSTEMS

PERFORMANCE & DONNÉES

SpatialGrid

AREA OF INTEREST

Grille spatiale hachée : insertion, suppression et déplacement en O(1), re-hash uniquement quand l'entité change de cellule, requête sur les 3×3 cellules voisines. L'inverse de la taille de cellule est pré-calculé pour éviter une division par entité.

DatabaseManager

BASE ASYNCHRONE

SQLite en mode WAL avec un thread worker dédié alimenté par une file concurrente : écritures en fire-and-forget, lectures avec callback renvoyé au thread de jeu. La boucle principale ne bloque jamais sur le disque.

Repositories

STOCKAGE DÉCOUPLÉ

Comptes et profils joueurs passent par des interfaces IAccountRepository / IPlayerRepository : le jeu ne connaît pas SQLite.

SECURITY

AUCUNE CONFIANCE DANS LE CLIENT

  • > Mots de passe Hachés en Argon2id avec libsodium.
  • > Anti brute-force Limitation des tentatives de login par IP sur une fenêtre glissante.
  • > Validation serveur Authentification vérifiée dans chaque handler, variations de ressources bornées : un client modifié ne peut rien s'octroyer.
  • > Reconnexion rapide Jeton de session généré côté serveur pour reprendre la partie sans repasser par le login après une coupure mobile.
